# 디자인 정책 (UI 검수에 필요한 핵심만)

토스의 공개 발표와 [Frontend Fundamentals](https://frontend-fundamentals.com)를 일반화한 개인용 기준이며, 토스의 공식 표준이 아니다. 조사 절차, 지표, 제품 전략은 다루지 않는다.

## 통제권·예측 가능성·투명성
- 닫기·건너뛰기·되돌리기를 언제나 준다. 사용자를 가두는 화면을 만들지 않는다.
- 같은 모양은 같은 동작을 한다. 같은 동작은 화면마다 같은 자리, 같은 아이콘, 같은 이름을 쓴다.
- 무엇이 왜 보이는지 알 수 있어야 한다(추천, 잠김, 비용).

## 상태 계약
모든 조작 요소와 화면에서 다음 상태를 그리고 검사한다.
- 기본, 마우스 올림, 초점, 눌림, 선택됨
- 불러오는 중, 사용할 수 없음(이유 표시), 오류(무엇이 왜 실패했고 어떻게 다시 하는지), 빈 상태
- 실패 뒤 복구: 다시 시도, 입력값 보존

## 복잡성은 제품이 흡수한다
- 안전한 기본값과 미리 채우기를 쓴다. 사용자가 값을 안다고 전제하지 않는다.
- 되돌리기 어려운 결정(삭제, 공개 범위, 결제)은 사용자가 확인하고 고칠 수 있게 한다.
- 초보자 화면이라도 위험과 결과는 숨기지 않는다.

## 보조 기술을 먼저 생각한다
- ARIA보다 원래 HTML의 의미(button, a, label, dialog)를 먼저 쓴다.
- 기본 검증에 다음을 넣는다: 확대, 좁은 화면, 고대비·강제 색상(`forced-colors`), `prefers-reduced-motion`, 스크린리더의 상태 전달
- 끌기 같은 포인터 동작이 핵심이면 탭·키보드로 같은 결과를 내는 대안을 둔다. 순서 변경을 알리고, 끝나면 초점을 예측 가능한 곳으로 되돌린다.

## 실기기 검증
- ARIA를 붙였다고 끝내지 않는다. iOS·Android를 포함한 실제 기기와 실제 스크린리더에서 이동, 알림, 초점 복원을 확인한다.
- 저사양 기기에서도 의미와 조작이 보존되는지 본다.

## 숫자 근거
- 확인되지 않은 숫자를 지어내지 않는다. 기준값은 사용자 결정, WCAG, 프로젝트 기존 기준에서만 가져온다.
- 새 기준이 필요하면 '예시' 또는 '정할 값'으로 표시하고 사용자에게 묻는다.
