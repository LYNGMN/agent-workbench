# 캐싱 아키텍처

## 원칙

캐시는 원본의 **복사본**이다. 성능 이득뿐 아니라 오래된 값, 무효화, 장애 시 원본 부하를 함께 설계한다. 캐시 도입을 전제로 삼지 말고 측정된 병목과 허용 가능한 최신성으로 필요성을 입증한다.

## 참조 문서 선택

| 요청 | 먼저 읽을 문서 |
|---|---|
| HTTP 헤더, 브라우저, CDN, 개인화 응답 | [HTTP·엣지 캐싱](references/http-edge-caching.md) |
| 로컬/분산 캐시, 키·TTL·무효화 설계 | [애플리케이션·분산 캐싱](references/application-distributed-caching.md) |
| Redis 메모리, eviction, HotKey/BigKey, 운영 진단 | [Redis 캐시 운영](references/redis-cache-operations.md) |

관련 문서만 읽는다. Redis 랭킹·트랜잭션·Pub/Sub·Streams는 캐시 운영과 직접 관련될 때만 다룬다.

## 작업 절차

1. **모드와 근거를 확인한다.** 새 설계, 기존 설계 검토, 장애 진단 중 하나를 정한다. 현재 p50/p95/p99, 처리량, 원본 부하, hit ratio, 오류율이 없으면 필요한 측정을 먼저 제안한다.
2. **데이터를 분류한다.** 항목마다 변경 빈도, 공유 범위, 크기, 민감도, 허용 stale 시간, miss 비용을 적는다. 성격이 다른 필드는 별도 키·정책으로 나눈다.
3. **가장 가까운 안전한 계층을 고른다.** 브라우저 → CDN → 로컬 → 분산 캐시 순서로 검토하되 개인화·일관성·동기화 비용 때문에 제외한 계층도 설명한다.
4. **수명주기를 완성한다.** 캐시 키 차원, freshness 예산, TTL 근거, 무효화 소유자와 순서, miss 경로, 캐시 장애 시 제한된 fallback을 정한다.
5. **집중 부하를 분리한다.** stampede, penetration, avalanche, pollution, HotKey, BigKey를 같은 문제로 취급하지 말고 각각의 증거와 완화책을 연결한다.
6. **검증한다.** 변경 전후 hit ratio, p95/p99, 원본 QPS, eviction, stale/error 비율을 같은 부하에서 비교하고 롤백 조건을 둔다.

Redis 장애 진단에서는 `INFO stats`, `INFO memory`, `SLOWLOG`, latency 도구, `--keystats`, `--bigkeys`, `--memkeys`, `--hotkeys`를 각각 검토한다. 실행하지 않을 도구도 지원 버전, 스캔 부하, 복제본·저부하 창, LFU 조건 중 해당 이유를 명시한다.

## 응답 형식

### 목표·근거·가정

측정값, 최신성·보안 제약, 아직 확인하지 못한 가정을 분리한다.

### 결정표

| 데이터/응답 | 계층 | 키 차원 | 최신성 예산·TTL 근거 | 무효화 | miss·장애 동작 |
|---|---|---|---|---|---|

### 위험과 완화

개인정보 공유, stale 데이터, stampede, 메모리 압박, 원본 과부하를 해당 설계와 연결한다.

### 검증 방법

관찰 지표, 부하/배포/장애 시험, 성공 기준과 롤백 기준을 제시한다.

## 안전장치

- TTL을 임의의 정답처럼 만들지 않는다. 알려진 stale 한도에서 역산하고, 수치가 없으면 “측정 후 정할 시작 범위”라고 명시한다.
- 개인화 응답은 사용자·테넌트·권한이 완전히 격리되지 않으면 공유 캐시에 저장하지 않는다.
- 키와 로그에 비밀번호, 토큰, 원문 개인정보를 넣지 않는다.
- 캐시 미스 시 무제한으로 원본에 우회시키지 않는다.
- CDN 기능, Redis 명령·정책은 공급자와 실제 버전의 공식 문서로 확인한다.
- 새로운 캐시 계층보다 기존 쿼리·인덱스·전송량 개선이 더 단순하면 그 대안을 우선한다.

## 짧은 예

상품 설명은 10분 stale 허용, 가격은 5초만 허용된다면 한 객체를 같은 TTL로 저장하지 않는다. `product:{id}:description`과 `product:{id}:price`처럼 수명주기를 분리하고, 가격 쓰기 성공 뒤 가격 키 무효화의 소유자와 순서를 명시한다. 실제 TTL은 각 stale 예산 이내에서 갱신 지연과 부하 시험으로 정한다.
