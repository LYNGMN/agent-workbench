# D1: limits local SQLite does not enforce

Test helpers usually run on local SQLite (often Python 3.9 `sqlite3`, no `setlimit`), so these never fail in tests. Add a guard test that imitates the D1 limit when the shape can grow.

| Fact | First seen | Guard |
|---|---|---|
| A compound SELECT with **6 or more UNION terms** fails: `too many terms in compound SELECT` (5 pass). Local SQLite allows 500. | 2026-10-01, admin page 503 for 12 h after one more list item | Never build UNION chains from a variable-length list. Bind a JSON array and use `json_each(?)` as one term. |
| A result row with **more than 100 columns** fails: `too many columns in result set`. Local SQLite allows 2,000. | 2026-10-23, a daily backup silently stopped for two weeks (99 → 134 tables, one column per table) | No SELECT that adds a column per table/item. Test with a 100-column fake. |
| `WITHOUT ROWID` tables break backup and D1 copy tools that page by rowid. | 2026-10-15 | Ordinary rowid tables; keep PRIMARY KEY / UNIQUE. |
| Free plan: 5M rows read/day and **50 queries per invocation**; over the read limit the DB refuses requests until the 00:00 UTC (09:00 KST) reset. | 2026-09-24/25 | Queue messages sized to the per-invocation limit (20 → 3 items). Cost rules: cloud-cost-guard. |
| Correlated subqueries in the SELECT list of a sorted, limited query run for every matching row before LIMIT. | 2026-09-25, 247k rows per page | Pick the page first (`WITH page AS MATERIALIZED (… LIMIT ?)`), then join extras. GROUP BY in the same batch instead of COUNT per row. See cloud-cost-guard query-patterns.md. |
| Workers Paid raises the per-invocation limit to **1,000 queries**, not unlimited: 10 calls × 101 statements broke it. | 2026-10-15, backfill job | Count statements per invocation (calls per tick × statements per call) and keep them under 1,000; lower the batch, not the check. |
| A heavy cron that shares an invocation with other cron work shares its query budget: the backup broke the transcript budget on the same `*/5`. | 2026-10-02, daily backup | Give heavy jobs their own cron expression (`3-58/5` next to `*/5`) so each invocation has its own budget. |
| `json_extract` throws on malformed JSON, failing the whole query. | 2026-10-21 | Wrap it: `CASE WHEN json_valid(col) THEN json_extract(col, '$.x') END`. |
| `wrangler d1 export` fails on a database with FTS tables. | 2026-10-10, D1 split | Copy with a Worker-side copier (page by rowid) instead of export/import. |
| SQL text that starts with `--` (a comment) is not passed safely as `--command <sql>`. | 2026-10-01 | Use `--command="$(cat file.sql)"` (with `=`), or `--file`. |

## Migrations on production
- Apply **one file at a time** (`wrangler d1 execute <db> --remote --file <file>` plus the `d1_migrations` row, or the project's guarded wrapper), not `migrations apply` of a backlog. A held file then cannot slip in with others.
- Record a Time Travel bookmark right before applying (`wrangler d1 time-travel info <db>`), so the database can return to that moment.
- With several Cloudflare accounts, pin `CLOUDFLARE_ACCOUNT_ID` in the command.
- Schema changes, data deletion and copies across databases are outside a normal deploy approval: ask separately with the impact.

## Splitting or routing several databases
- Keep a single table → database map in code (e.g. `src/db-tables.js`), and never mix tables of two databases in one statement or batch.
- Every new table is registered in that map; tests run against the split setup.

## Backups (suggested layers)
| Layer | Covers |
|---|---|
| D1 Time Travel, 30 days | a bad deploy or migration (whole DB to a moment) |
| Encrypted daily copy to R2 with a bucket lock | one table or one user's data damaged |
| The same copy in another cloud with object lock | Cloudflare account lost or compromised |

Uploads use `If-None-Match: *` so a file is never overwritten. A per-table copy taken over minutes is not a snapshot; use Time Travel for one moment.
