# Versioned Release & Clean Code Governance

버전명 파일 관리, 버전 미포함 일반 파일 수정 원칙, 파일명 명명 기준, 변경 내역 문서 분리, 100% 완전한 최종 배포판 코드 제공 원칙을 규정합니다.

---

## 핵심 5대 작업 원칙

### 1. 버전명 파일 보존 및 신규 파일 생성 (Versioned File Immutability)
- 파일명에 버전(예: `_V1.0.0`, `_V2.0.0`, `_v1.18.60`)이 명시된 파일은 이전 이력 보존과 참조 무결성을 위해 **절대 덮어쓰거나 인플레이스(in-place)로 수정하지 않습니다**.
- 코드 개선이나 기능 확장, 정식 패치 릴리스가 발생하면 반드시 버전 규칙(SemVer)에 따라 버전 번호를 올린 **새 파일(예: `_V2.0.1.pine`)을 신규 생성**합니다.
- 기존 버전 파일은 원형 그대로 보존합니다.
- **[작업 중 미완성/동작 오류 수정 예외]**: 방금 작업했거나 현재 개발·테스트 중인 특정 버전 파일에서 기능이 정상 작동하지 않아 오류를 바로잡거나 동작을 수정하는 단계에서는 매번 새로운 버전 파일을 만들 필요 없이 **현재 작업 중인 파일 내에서 직접 수정(in-place)**하여 완성합니다. (검증이 완료된 안정 버전에 새로운 기능 추가나 별도 릴리스를 진행할 때만 새 버전을 생성합니다.)

### 2. 버전 미포함 파일의 기본 수정 원칙 (Unversioned File In-Place Update)
- 파일명에 버전명이 포함되어 있지 않은 일반 소스 코드 파일(예: `check-static.mjs`, `index.ts`, `App.vue`, `style.css` 등)은 사용자의 별도 요청("새 파일로 만들어줘", "버전 분리해줘" 등)이 없는 한 **기존 파일을 인플레이스로 직접 업데이트**합니다.
- 임의로 파일명 뒤에 `_new`, `_v2`, `_temp`, `_copy`, `_final` 등의 임의 접미사를 붙여 불필요한 파편화 파일을 생성하는 행위를 엄격히 금지합니다.

### 3. 파일명 명명 기준 (File Naming Conventions)
- **버전 파일**: `<기본이름>_V<Major>.<Minor>.<Patch>.<확장자>` 형식을 표준으로 사용합니다 (예: `trend-line_V2.0.1.pine`).
  - **Patch (`0.0.X`)**: 버그 수정, 성능 최적화, 툴팁 개선, 내부 리팩터링 등 기존 인터페이스와 동작이 호환되는 개선.
  - **Minor (`0.X.0`)**: 새로운 기능 추가, 신규 입력 파라미터나 신규 지표/신호 로직 확장 등 하위 호환 가능한 기능 추가.
  - **Major (`X.0.0`)**: 아키텍처 개편, 파괴적 변경(Breaking Changes), 대규모 구조 재설계.
- **일반 파일**: 프로젝트 및 언어 생태계 표준 관례를 철저히 준수합니다.
  - Node / Web / 유틸리티: 소문자 케밥 케이스(`kebab-case.ext`, 예: `check-static.mjs`)
  - 컴포넌트: 파스칼 케이스(`PascalCase.ext`, 예: `TrendLineCard.tsx`)
  - Python: 스네이크 케이스(`snake_case.py`)
  - 의도가 명확하고 축약되지 않은 단어를 사용하며, 임의의 번호나 임시 표식을 붙이지 않습니다.

### 4. 업데이트·변경 내역의 독립 문서 분리 및 버전 미포함 파일 주석 원칙 (Changelog Separation & Unversioned Notes)
- 코드 파일 내부에 장황한 수정 이력, 업데이트 기록, 날짜별 주석 블록을 달지 않습니다.
- 모든 변경 사항, 최적화 수치, 벤치마크 결과, 버그 수정 내역은 코드와 분리하여 **독립 문서(`CHANGELOG.md` 또는 `docs/` 내 릴리스 노트)**에 체계적으로 기록합니다.
- 코드 내부에는 정말 불가피한 핵심 요약 1줄만 예외적으로 허용하되, 가급적 주석 공해(comment pollution)가 없는 완전한 클린 코드를 유지합니다.
- **[버전 미포함 파일의 핵심 변경 주석 허용 및 누적 금지]**: 파일명에 버전명이 붙지 않아 하나의 파일을 계속해서 수정하는 방식의 일반 파일인 경우, 이전 버전과 새로운 버전 간의 차이를 명확히 구분하고 추적할 수 있도록 파일 상단 헤더 또는 해당 로직 위치에 **최신 핵심 변경 내용(수정 일자, 목적, 핵심 변경점 1~3줄 요약)을 주석으로 작성**하는 것을 적극 권장합니다. **단, 과거 이력을 코드 내에 체인지로그처럼 계속해서 덧붙여 누적하는 행위는 절대 금지**하며, 항상 최신 변경 내용 1개 세트로 갱신·대체합니다. 모든 누적 변경 이력은 반드시 `CHANGELOG.md`에만 기록합니다.

### 5. 100% 완전한 최종 배포판(Production-Ready) 형태 제공
- 코드를 제공할 때는 일부분만 생략하거나(`// ... existing code ...`), diff 조각만 제시하거나, 미완성 플레이스홀더를 남기는 행위를 절대 금지합니다.
- 사용자가 즉시 복사하여 트레이딩뷰 파인 에디터나 프로덕션 환경에 붙여넣어 실행할 수 있는 **100% 완전한 전체 코드**로 제공합니다.

### 6. 툴팁 및 서비스 UI 텍스트 단어 끊김 방지 (Word-break & Wrap Integrity)
- **대원칙: 단어 중간에 줄바꿈되지 않게 명료하게 작성하는 것을 원칙으로 합니다.**
- 툴팁(`tooltip`), 인풋 타이틀/라벨, 차트 UI 안내 문구, 서비스 UI 설명, 메뉴명을 작성할 때는 글자나 단어 중간에서 어색하게 끊겨서 줄바꿈(단어 쪼개짐)되지 않도록 항상 유념합니다.
- 문맥과 의미 단위(어절 단위)로 매끄럽게 끊기도록 작성하며, 긴 문장은 인위적인 단어 절단을 피하고 명시적 줄바꿈(`\n`)을 적절히 배치하여 가독성을 극대화합니다.
- 일반 웹/서비스 UI 환경에서는 `word-break: keep-all` 스타일과 `white-space: nowrap`을 적극 고려하고, 조사나 복합 단어가 어색하게 잘리지 않도록 정돈합니다.

## 표준 작업 흐름

1. **대상 파일 검토**:
   - 파일명에 버전 식별자(`_V...`)가 있는지 확인.
2. **분기 처리**:
   - **버전 파일**: SemVer 기준(Patch/Minor/Major)으로 새 버전 파일명을 결정하고 신규 파일 생성.
   - **일반 파일**: 별도 요청이 없다면 기존 파일을 인플레이스로 수정.
3. **CHANGELOG 작성**:
   - 변경 내역을 `CHANGELOG.md` 문서에 체계적으로 기록.
4. **검증 및 최종 보고**:
   - 관련 테스트 및 컴파일러 진단 도구 실행 후 100% 최종 배포판 상태 보고.
