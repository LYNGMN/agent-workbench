# 전역 에이전트 지침 (agent-workbench 틀)

이 파일은 agent-workbench가 깔아 주는 시작용 틀입니다. Codex(`~/.codex/AGENTS.md`), Antigravity(`~/.gemini/GEMINI.md`), DeepSeek Harness(`~/.dsh/AGENTS.md`)가 함께 쓸 수 있게 도구 이름에 묶이지 않은 규칙만 담았습니다. 자기 방식에 맞게 고쳐 쓰세요. 프로젝트의 `AGENTS.md`·`CLAUDE.md`가 있으면 그쪽이 더 구체적이므로 우선합니다.

## 1. 언어와 보고

- 사용자에게 보이는 글(답변, 진행 상황, 질문, 최종 보고)은 항상 한국어로 쓴다. 영어 도구 결과나 오류를 읽은 직후에도 마찬가지다.
- 코드, 커밋 메시지, 파일 경로, 명령어, 식별자는 원래 표기를 유지한다.
- 사용자가 개발자가 아닐 수 있다. 결정에 필요한 말로 설명하고, 결과만 요청하면 설명을 줄인다.
- 끝낼 때는 바꾼 것, 검증한 것, 검증하지 못한 것, 배포·커밋 여부를 나눠 보고한다. 검증하지 않은 것을 된 것처럼 말하지 않는다.

## 2. 작업 원칙

- 구현 전에 관련 파일과 미커밋 상태(`git status`)를 확인한다. 큰 변경은 계획을 먼저 보여 준다.
- 변경은 작고 검증 가능한 단위로 한다. 불필요한 리팩터링과 새 의존성을 피한다.
- 새 기능·도구를 만들기 전에 이미 있는 것(저장소 안 코드, 설치된 스킬, 외부 패키지)을 먼저 찾는다.
- 테스트할 수 있는 변경은 실패 테스트부터 만든다. 완료를 말하기 전에 새로 실행한 검증 결과를 확인한다.
- 민감 정보(.env, 키, 토큰, 쿠키)는 출력하지 않는다. 사용자에게 키를 채팅으로 달라고 하지 않는다.
- 로컬 개선 요청을 게시·배포·병합 요청으로 넓히지 않는다. 합의된 범위와 승인을 반복해서 묻지 않는다.

## 3. 승인이 필요한 일

다음은 사용자가 이번 작업에서 분명히 승인한 뒤에만 한다. 가능하면 사용자가 직접 실행할 한 줄 명령(여러 번 돌려도 같은 결과)을 준비해 보여 준다.

- 운영 배포, 원격 데이터베이스 변경·대량 쓰기·삭제
- DNS·라우트, 예산·요금제·한도, 시크릿 등록·복사(시크릿은 사용자가 직접 넣는다)
- Git: 첫 Push, 새 remote, 병합, 공개 전환. 기본 브랜치 직접 수정, `main` 직접 Push, 강제 Push는 하지 않는다
- 되돌리기 어려운 정리: `git clean`, `git reset --hard`, `git checkout .`, 폴더 삭제

## 4. Git

- 기본 브랜치(`main`)에서 바로 고치지 않는다. 목적 하나에 브랜치 하나(`<도구>/<종류>/<목적>`, 종류는 `feat`·`fix`·`docs`·`chore`).
- 커밋 하나에 의도 하나. 메시지에 이유를 쓰고, 커밋 전에 민감 정보가 없는지 본다.
- 여러 작업본(worktree)을 쓰면 `git stash`를 쓰지 않는다. 모든 작업본이 같은 stash 목록을 써서 다른 작업의 stash가 풀릴 수 있다. 대신 `git diff > <임시폴더>/patch`로 빼 두었다가 `git apply`.

## 5. 셸에서 자주 걸리는 것

- zsh는 `$변수`를 단어로 나누지 않는다. `node --test $T`는 파일 0개로 "fail 0"이 나온다. 배열 `"${T[@]}"`를 쓰고 실행된 테스트 수를 확인한다.
- 대기 반복문 안의 `pgrep -f "패턴"`은 자기 자신과 맞아 끝나지 않는다. `pgrep -f "[n]ode …"`처럼 대괄호를 쓰거나 로그의 끝 표시를 기다린다.

## 6. 스킬 고르기

단순하고 분명한 요청은 스킬 없이 처리한다. 전문 절차가 필요하면 지금 단계의 담당 스킬 하나와 그 필수 의존성만 쓴다(`skill-router`). 단계가 바뀔 때 다음 스킬로 넘긴다. `using-superpowers`의 "모든 대화에서 스킬 호출" 규칙은 쓰지 않는다.

묶음 스킬(gstack·superpowers·pstack)은 사람이 부를 때 `<팩>-<이름>`이다(예: `/gstack-browse`, `/superpowers-brainstorming`). 모델이 스스로 부를 때는 원래 이름을 쓴다. 스킬을 설치하거나 지운 뒤에는 `~/.agents/bin/pack-prefix-sync --apply`, `antigravity-sync-skills --apply`, `dsh-sync-skills --apply`로 도구별 이름을 다시 맞춘다.

| 작업 | 담당 스킬 | 함께 쓰는 것 |
| --- | --- | --- |
| 새 기능·동작 변경, 의도가 흐림 | `brainstorming` | — |
| 여러 단계 구현 | `writing-plans` | — |
| 원인 모를 오류·테스트 실패 | `systematic-debugging` | — |
| 완료·통과 주장 직전 | `verification-before-completion` | — |

| UI를 만들거나 바꾼 뒤 | `ui-visual-qa` | `wcag22-vibe-coding` |
| 아이콘·SVG·로고 | `icon-svg-implementation` | — |

| Google Apps Script(clasp, 트리거) | `apps-script-ops` | — |

## 7. 교훈 남기기

- 작업 중 새로 배운 사실(도구의 함정, 플랫폼 제한, 사고 원인)은 그 프로젝트 `AGENTS.md`의 "작업하며 배운 것"에 한 줄로 남긴다. 형식: `사실 — 처음 본 날(YYYY-MM-DD) — 막는 방법(테스트·스크립트·규칙)`.
- 같은 규칙을 여러 파일에 복사하지 않는다. 그 규칙이 맞는 가장 좁은 곳 한 군데에 둔다.
- 같은 사고가 두 번 나면 테스트나 검사 스크립트로 막자고 제안한다.
